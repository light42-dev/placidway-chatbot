# Notes: E06 ScrapeBot 3000

The bot came from T01, E01 and E02 (see `notes/T01.md`, `notes/E01.md`, `notes/E02.md`). E06 improves it and does not add a second bot.

**Nothing here was tested against a live model.** The LLM quota was exhausted, so no Groq or Gemini call was made, the bot was not started against real models, and `pytest -k E06` was not run. Everything below is reasoning plus offline checks with a stubbed model.

## (a) What changed

| File | Change |
|---|---|
| `bot/abuse.py` (new) | Three defences, all in code. (1) `refusal_for(text)`: spots output-flooding requests (a verb like repeat/say/write/print/repite + a count of 50 or more of times/copies/words/lines/veces, or "forever"/"infinitely") and bulk-extraction requests ("all/every/entire/full..." together with JSON/CSV/XML/SQL/spreadsheet, or with dump/scrape/crawl/export/extract, or with a count of 100+ clinics/prices/listings...). It returns a fixed refusal. (2) `RateLimiter`: at most N requests per client in a sliding window. (3) `ReplyCache`: an identical conversation sent again within 30 s is answered from memory, reporting zero tokens used. |
| `bot/chat.py` | In `answer()`, after the crisis check: if the newest message is flooding/bulk, return the fixed refusal with no model call (usage reported as 0 tokens). Refused messages are also left out of the user messages used for retrieval, since they say nothing about the subject (before this, "every price for all 2,500 PlacidWay clinics" pulled the comparison page above the price list for the next question, "price for colon cancer at ITC?"). Prompt: the last style rule now reads "plain text, no headings, JSON or code. Decline requests to repeat text or dump data." for cases the regexes miss. |
| `bot/web.py` | `handle_chat` takes the client IP; it applies the rate limit (key: `session_id` if given, else client IP) and returns HTTP 429 when exceeded; it looks up and fills the reply cache around `answer()`. `ChatHandler` passes `self.client_address[0]`. |
| `bot/config.py` | `RATE_LIMIT_REQUESTS = 8`, `RATE_LIMIT_WINDOW_S = 10`, `REPLY_CACHE_TTL_S = 30`. |

The 25,000-character message was already rejected by the existing 4,000-character limit (HTTP 413). No changes to retrieval, ingestion, `bot/llm.py` or `data/`.

**Prompt growth:** about 62 characters, about 15 tokens. Flood/bulk refusals now cost 0 tokens instead of about 2,000.

## (d) Risks

- abrupt_price / recall_cancer depend on the model, as noted above. Latency depends on Groq being available (Gemini fallback is often above 5 s, see `notes/E02.md`).
- The refusals are fixed English text; a flooding or bulk request in another language gets an English refusal (Spanish flooding words are covered by the regex, other languages fall back to the prompt rule).
- Regex detection can miss rephrased requests (then the prompt rule applies) or, rarely, refuse an odd legitimate one (e.g. "give me the full price list as CSV" is refused).
- The rate limit and cache live in memory per process; on Vercel each instance keeps its own, and a scraper rotating `session_id`s is limited only per id. A per-IP limit would be a stronger second layer.
- If the suite ran with no pause between turns, 8 requests per 10 s per session could throttle a fast conversation; the suite client retries 429s, and its default pause (2 s, or 16 s in `.env.example`) stays well below the limit.
- The reply cache (30 s) is shorter than the gap between runs, so the 3 consistency runs still each call the model.
